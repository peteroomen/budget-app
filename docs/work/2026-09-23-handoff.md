tokens: recap 1024→4096, chat 2048→8192, categoriser 4096→8192. The PDF parser already had 16000.
No `thinking`, `temperature` or `top_p` is passed anywhere, so nothing else needed changing.

Previously verified at the pre-merge head: 39 tests locally and in CI, lint, type-check, production build,
Vercel preview build, linking controls exercised with synthetic stubs, import flows exercised with synthetic
Akahu responses and PGlite. **None of that touched live ANZ auth, production migrations, or a real import.**

### Remaining steps, in order

1. Restore the Supabase project (§2) — **ask first**.
2. Read production migrations; determine which of the three are unapplied and in what order they must run.
3. Confirm production configuration exists (names in `.env.example` and `src/lib/bank/config.ts`):
   `AKAHU_APP_TOKEN`, `AKAHU_USER_TOKEN`, `AKAHU_OWNER_USER_ID`, `AKAHU_HOUSEHOLD_ID`, `CRON_SECRET`,
   `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_SUPABASE_URL`, `BANK_SYNC_ENABLED=false`.
   `bankConfig()` returns `null` unless **all** are present _and_ `VERCEL_ENV === 'production'` — so a
   missing variable presents as a silently disabled feature, not an error. Check presence, never values.
4. Link the ANZ account in Settings → Accounts; run a **manual** sync (allowed while `BANK_SYNC_ENABLED=false`).
5. Compare imported rows against a real bank statement.
6. Only after that comparison succeeds: set `BANK_SYNC_ENABLED=true`.

### Behaviour worth remembering

One Akahu user bound to one Tide owner and household · ANZ NZD checking/savings with transaction access ·
settled transactions only · reads Akahu's cache, does not force a bank refresh · daily cron `0 17 * * *`
UTC · history builds up gradually · account mapping is fixed after creation, no unlink/remap UI · the
suggested cutover date is not proof of statement coverage · provider refresh timestamps are a consistency
check, not a snapshot guarantee · a replaced provider transaction ID is treated as a new transaction, and
annotations/tombstones are not guessed across it · **ambiguous statement overlap stops reconciliation —
never delete legitimate data to make it proceed.**

Four decisions the user confirmed on 2026-09-18:

|            |                                                                                                                 |
| ---------- | --------------------------------------------------------------------------------------------------------------- |
| Content    | Deterministic digest + a 2–3 sentence Claude note. A failed AI call drops the note only; the email still sends. |

| Recipients | Household-level toggle and send day on `households`; sends to every member's `profiles.email`.                  |
| Provider   | Resend, with an ADR (`docs/decisions/` has no email decision yet).                                              |

Model for the note: **`claude-sonnet-5`**, matching §3.

**PR #41 made this plan smaller.** The revision table at the top of the plan file is the authoritative
list; the essentials:

- A service-role Supabase client already exists (`src/lib/bank/sync.ts` via `bankConfig()`) — reuse it,
  don't add a second.
- A cron route already exists (`src/app/api/cron/bank-sync/route.ts`) with a timing-safe bearer check.
  **Copy its auth block verbatim** — it compares `byteLength` before `timingSafeEqual`, which throws on a
  length mismatch.
- `src/lib/supabase/middleware.ts:16` already early-returns for `/api/cron/bank-sync`. Generalise that to
  the `/api/cron/` prefix rather than adding a second special case.
- `vercel.json` already has one cron. Weekly email is a **second** entry — confirm the account's cron
  allowance covers two.
- **`bankWarnings()` / `bankStatus()` in `src/lib/bank/status.ts` already produce freshness and
  incomplete-history warnings** for the recap and chat. The email's data-freshness requirement is mostly
  satisfied by reusing them. Do not write a second freshness rule.
- **Migration timestamp `20260918000000` is taken** by `20260918000000_anz_bank_sync.sql`. Use
  `20260923000000_weekly_emails.sql`.

Still genuinely unsolved in the plan: `financial_snapshot(date,date)` is `security invoker` and derives the
household from `auth.uid()`, so a cron request cannot use it. A `security definer`

The "transactions needing review" figure the project goals ask for depends on Workstream C. If emails ship
