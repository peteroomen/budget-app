# UX Polish: Category Cleanup, Global Month, Budget Drill-down

**Date:** 2026-06-02  
**Branch:** feature/ux-polish-33-34-35  
**Roadmap item:** Phase 5 — Polish (misc QoL issues from #33, #34, #35)

## Goal

Three small but meaningful UX improvements in one slice:

1. **#33 — Category cleanup:** Merge "Dining Out" + "Takeaways" → "Dining & Takeaways" (already on roadmap), and lift the blanket `is_system` deletion block so users can remove system categories they don't want.
2. **#34 — Month persists across pages:** When navigating via the sidebar or bottom tab bar, the currently-selected month carries forward instead of resetting to the current month.
3. **#35 — Budget row drill-down:** Each category row on the Budgets page gets a small link that opens the Transactions page filtered to that category + month.

## Approach

### Issue #33 — Category cleanup

Two parts:

**A. Merge Dining Out + Takeaways**

A single SQL migration:

1. Find/create "Dining & Takeaways" (rename "Dining Out" in-place via UPDATE — preserves its ID, so all FK references migrate for free).
2. Reassign all transactions where `category_id = <Takeaways id>` → `<Dining & Takeaways id>`.
3. Reassign all `merchant_category_map` rows the same way.
4. DELETE the "Takeaways" row.

Renaming in-place is cleaner than creating a new row + reassigning all FKs.

**B. Allow deleting system categories**

Currently the category management UI (likely in `SettingsPage` or `CategoryList`) hides or disables the delete action for `is_system = true` rows. Fix: remove that guard. Add a more prominent confirmation dialog for system categories that warns "This is a default category — deleting it will remove the category from all transactions that use it." The server action already sets `category_id = NULL` on delete via the FK `ON DELETE SET NULL`.

No schema changes needed. No new `description` field — the issue mentions it but it's a separate feature and adds complexity; excluded from this slice.

### Issue #34 — Month persists across pages

**Chosen approach: month-aware nav links.**

`SidebarNav` is a non-client server component that renders static hrefs. `BottomTabBar` is already a client component (uses `usePathname`). The plan:

- Convert `SidebarNav` to a client component that also reads `useSearchParams()`.
- For both `SidebarNav` and `BottomTabBar`, when building each nav link href, if the current URL has a `?month=YYYY-MM` param and the target page is one of `[/dashboard, /budgets, /summary, /transactions]`, append `?month=YYYY-MM` to the target href.
- Pages that don't use month (`/accounts`, `/import`, `/chat`, `/settings`, `/admin`) get plain hrefs.

The per-page `MonthSelector`/`MonthPicker` components are unchanged — they continue to update `?month=` on the current page. The nav layer just carries that param forward when the user switches pages.

A helper array `MONTH_AWARE_ROUTES = ['/dashboard', '/budgets', '/summary', '/transactions']` keeps the logic explicit.

### Issue #35 — Budget row drill-down

The Transactions page already supports `?cat=<UUID>&month=YYYY-MM` URL params (confirmed in `TransactionFilters.tsx` line 44).

In `BudgetList` (or whichever component renders each budget row), add a small icon button (Lucide `ListFilter` or `ExternalLink`) at the right of each row. It renders as a Next.js `<Link>` to `/transactions?cat=${category.id}&month=${month}`. On hover, tooltip: "View transactions".

For mobile (card grid layout), add the same link as a secondary action below the spend/budget figures.
